## Phase 7

- **2026-09-02** — 07 §Ratings says "floor: highest level band with ≥2 tracked atoms", which reads as a floor but cannot be one (it would pin the level to the hardest material learned). Implemented as a **clamp**: the level is bounded to the range of levels where a challenge is actually constructible — at least 2 tracked, drillable atoms inside the ±5 band. This matches the paragraph above it ("the rating can't exceed what the path has taught"), gives demotion a real floor at the bottom of that range, and makes a challenge always buildable. Extends 07.
- **2026-09-02** — A fresh strand starts at the **bottom of its supported range**, not level 1: with only hard material tracked, level 1's band would be empty and no challenge could be generated.
- **2026-09-02** — `atoms.ts` gained drills for `spell:`, `keysig:`, `ear:`, `prog:`, `prog-smooth:` and `song:` atoms. Before this only note/fivefinger/scale/chord atoms were drillable, which meant the theory and ear strands had **zero** reviewable or ratable atoms — 07's review and rating designs both assume every tracked atom can be drilled. `keysig:*` drills as a roman-numeral card in that key (you cannot answer it without knowing the signature); the choice-mode card 06 imagines is still deferred.
- **2026-09-02** — Badges are computed purely from Dexie on every read (07: "all computed from Dexie, no new state"). The only stored badge state is the "already celebrated" snapshot used to fire the toast once.
- **2026-09-02** — `getRecap()` writes its computed recap to `meta`, so it is **not** liveQuery-safe. Split into `readRecap()` (read-only, for `useLiveQuery`) and `getRecap()` (computes once per week, called from an effect) — the same split `readTodaySession`/`getTodaySession` already used.
- **2026-09-02** — Passing a checkpoint now calls `trackAtoms` for stage units that are _already_ marked passed, instead of skipping them. - **2026-09-02** — `keysig:c:major` added to s5.u6. The `circle-complete` badge requires all 12 key signatures and the curriculum only defined 11 — C, the one signature with nothing in it, was missing.
- **2026-09-02** — PWA icons are generated by `scripts/make-icons.mjs`, a ~120-line rasterizer for the app mark, rather than committed binaries from an image toolchain. The mark is only rounded rectangles, so the renderer is a scanline fill plus `node:zlib`; regenerating needs no dependency.

## Rehearsal lint

_A second audit (2026-09-03) found that graded takes often scored material the unit never rehearsed. The lint below now stops it at commit time._

- **2026-09-03** — **New curriculum lint: "graded takes only score rehearsed material"** (`curriculum.test.ts`). The grammar lint proves a unit _has_ a ladder. It never checked that the ladder ramps the thing the graded take then scores, and 13 takes did not. The new rule: a graded take may change the **key**, the **tempo** and the **length** of what was rehearsed, and may not introduce a **motor pattern the learner has never made**. Rehearsal counts path-wide, because the path is gated. A tempo-mode take also needs a tempo-mode rehearsal at the same signature that reaches at least its BPM — nobody is scored faster than they were ramped.
- **2026-09-03** — The lint's "same motor pattern" test for `scale-run` is **the fingering array itself**, read from `scaleFingering()`. This is not a heuristic: C, G, D, A, E and B share one right-hand fingering, so laddering A and grading E is a genuine transposition test. B♭, E♭, A♭, D♭ and G♭ have five different right-hand fingerings, so grading E♭ after ramping B♭ is grading a hand shape that was never made. The left hand is the other way round — all the flat keys share one fingering. The distinction was already in `theory/scales.ts`; the lint just reads it.
- **2026-09-03** — Signatures deliberately exclude the key for every generator, and exclude the roman sequence for `progression-play`. Transposing a known shape and rotating a known loop are both skills the curriculum teaches on purpose (s3.u4 is _about_ rotation). Chord vocabulary is checked separately: every roman in a graded take must have been played somewhere earlier on the path.
- **2026-09-03** — `unseen-chart`, `note-find` and the three `ear-*` generators are exempt. The unseen chart is unseen by design; the others recognise rather than execute, which is the same reason `NO_MOTOR_PATTERN` exempts their units from the ladder rule.

## Desktop build

- **2026-09-06** — **Keysense ships as a Windows executable, built with Electron** (`electron/main.cjs`, `electron-builder.yml`). The app needs Web MIDI and Web Audio, and only a Chromium engine gives both. Electron carries its own Chromium, so the desktop app behaves exactly as the browser build does. The cost is size: the installer is about 139 MB. Tauri would be about 10 MB, but it runs on WebView2, where the MIDI permission path is less proven, and it needs a Rust toolchain on every build machine.
- **2026-09-06** — The shell serves `dist/` over a private URL scheme, `keysense://app/`, registered as standard and secure. Three things depend on this. The history router needs real paths, not `file://`. Web MIDI and the AudioWorklet need a secure context. Relative asset URLs in the build need an origin. A `file://` load fails all three.
- **2026-09-06** — **Electron asks for MIDI under the name `midiSysex`, even when the page requested `sysex: false`.** Our adapter always asks without sysex (`webmidiAdapter.ts`). Granting only `midi` leaves the app with no keyboard. Both names are in `ALLOWED_PERMISSIONS`; everything else is denied.
- **2026-09-06** — **The piano samples are now vendored.** `scripts/fetch-samples.mjs` reads the sample list out of the installed `smplr` bundle and downloads 226 OGG files (20 MB) into `public/samples/`. The desktop app must not depend on a GitHub Pages host being reachable. The files are **not committed**; `npm run samples` fetches them, and `npm run desktop:build` runs it first.
- **2026-09-06** — `sampler.ts` picks its `baseUrl` at load time. It sends one HEAD request for a local sample. If that answers, it plays from `public/samples/`; if not, it falls back to smplr's own host. So a bare checkout still makes noise, and no build flag is needed to tell the two cases apart.
- **2026-09-06** — **The desktop build skips the service worker.** A worker cannot register on a custom URL scheme, and it has no work to do: the app already carries every asset. `registerSW.ts` returns early when the preload's `keysenseDesktop` marker is present.
- **2026-09-06** — Android is **not** built yet. The same web build should wrap with Capacitor, but MIDI over USB inside an Android WebView needs its own proving pass, and the toolchain (Android Studio, a JDK) is not installed here.

## Tourist mode (2026-09-07)

- **2026-09-07** — Tourist mode is one setting (`tourist`, stored with the other preferences in `ks.settings.v1`) with one rule: every door opens, and nothing is recorded. The Path stops disabling locked nodes, and the lesson player gains a "Skip this step" button and a jump menu over the unit's steps. Extends 05 §Screens (Path, Lesson player).
- **2026-09-07** — The "record nothing" half is enforced in `src/progress/`, not in the screens. `src/progress/tourist.ts` holds the flag, and every progress write returns early while it is on: `saveTake`, `markUnitPassed`, `markUnitInProgress`, `completeUnit`, `gradeAtom`, `markBlockComplete`, `addPracticeMinutes`, `resolveRetest`, `saveResume`, `queueRetest`, `clearResume`, and the level write inside `recordChallenge`. Alternatives: guard each call site in the players. Reason: one rule in one layer covers every player, including the ones a tourist reaches by accident (drill, songs, rating, studio). - **2026-09-07** — The flag lives as a module-level boolean in `src/progress/tourist.ts`, not read from the settings store, because `src/progress/` may not import a store (01 §Module boundaries) and a write needs the value at call time, outside a React render. `initTouristMode()` in the settings store keeps the two in step and turns the mode on for a `?tourist=1` link.
